# Upstreams that speak only MCP 2026-07-28

- **Problem**: an upstream built on the official SDK with `legacy: 'reject'` refuses `initialize` with -32022; mesh7 retried forever and registered no tools. Servers on the SDK default (both eras) were never affected.
- **Decision**: mesh7 still opens every upstream with `initialize`; on a -32022 that offers 2026-07-28 it switches that upstream to the modern era: `server/discover`, no session, the per-request envelope in `params._meta`, and over HTTP the three headers derived from the body (`mcp/era.go`). Modern-only result fields (`resultType`, `ttlMs`, `cacheScope`, `_meta` serverInfo) stop at mesh7; a result that is not `complete` is an error.
- **Why**: legacy-first never disturbs an existing server (some old stdio servers exit on any request before `initialize`); headers built from the body cannot disagree with it (-32020).
- **Where**: `mcp/era.go`, `mcp/client.go` (connectModern, discoverTools), `mcp/transport_streamable.go`; tests in `mcp/era_test.go` against a Go copy of the strict SDK server; wire reference in `docs/internal/capture-mcp-2026-07-28-client.log`. Side fix: an `initialize` or `tools/list` answered with a JSON-RPC error is now a failed connect, no longer a silent success. Not done: MRTR (`input_required`), mesh7's own export in 2026.
