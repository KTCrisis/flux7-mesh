# A starting daemon holds a lock; clients wait for it

- **Problem**: a `mesh7 --mcp` client that found no daemon on the port ran standalone and served its approval API on that port. The daemon spends a few seconds initialising before it listens, so a client started in that window took the port; on void (2026-11-08 13:18) the daemon then failed with `address already in use` and restarted twelve times. When the daemon won instead, the client still ran as a second full mesh.
- **Decision**: the daemon (`mesh7 serve`, or `mesh7` without `--mcp`) takes an exclusive `flock` on `~/.cache/mesh7/<configID>.daemon.lock` before initialising and keeps it for its life. A client that finds no daemon on the port and sees the lock held waits for the daemon (30 s, `MESH7_DAEMON_WAIT`), then relays to it; with no lock it runs standalone as before.
- **Why**: the lock exists from the first instant of the daemon's process, the port only after initialisation; the kernel releases it however the daemon exits, so no stale state.
- **Follow-up (same day)**: the first version did not keep the locked `*os.File` referenced; its finalizer closed it at the next garbage collection and released the lock (seen free on void minutes after the restart). `heldLock` keeps it; a test forces `runtime.GC()`.
- **Where**: `cmd/mesh7/daemonlock.go` (+ `_unix.go`, `_other.go`: no lock on Windows, race unchanged there), `main.go`, `serve.go`; tests in `daemonlock_test.go`; reproduced with old and new binaries started together.
