# Tools are classified from what they declare; the control plane edits policy as text

- **Problem**: writing a policy meant judging every upstream tool from its description, the draft from `discover` denied every write and dropped MCP annotations, generic tools (SQL, shell, code, CLI dispatchers) looked like any other, and changing one tool's action meant hand-editing a YAML file ruled by first match.
- **Decision**: `registry.Classify` derives family (named, generic) and access (read, write, unknown) from declared metadata only, with reasons, the restrictive side winning on conflict; it drives the `discover` draft (named reads allow, the rest `human_approval`) and `GET /tools`. `GET /tools/decisions` (control plane) shows the static decision per agent. `PUT /policies/{agent}/tools/{tool}` inserts an exact rule before the deciding one, rewrites an exact rule in place, and removes only rules marked `# set from console`.
- **Why**: classification is advice, not enforcement, because every signal is an unverified claim; editing lines located through the YAML tree keeps comments and blank lines that a re-serialization loses; validating the whole set before applying, keeping a `.bak` and tracing `mesh.policy_edit` makes a policy change as auditable as a call.
- **Where**: `registry/classify.go`, `policy/engine.go` (`Explain`), `policy/edit.go`, `proxy/policy_edit.go`, `cmd/mesh7/discover.go`; public doc `mesh7/tool-classification` on docs.flux7.art.
