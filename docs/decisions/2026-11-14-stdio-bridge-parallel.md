# The stdio bridge relays requests in parallel once the session exists

- **Problem**: the `--mcp` shuttle read one line, waited for the daemon's answer, then read the next. A Claude session and all its sub-agents had one mesh7 call in flight: on 2026-11-14 a 1.4 s search waited 35 s behind a local model call. The daemon already served one session's requests concurrently; the shuttle was the queue.
- **Decision**: until `initialize` has minted the session, the shuttle relays one line at a time (notifications and client answers too). After that each request goes on its own goroutine, up to 8 at once (`MESH7_BRIDGE_PARALLEL`). Answers return in any order, matched by JSON-RPC id, and each written line stays whole. A daemon lost during a parallel call answers that id with a JSON-RPC error, then the shuttle stops as before. At end of input it waits for calls in flight.
- **Why**: sub-agents running in parallel must not be serialised by the proxy that governs them. Measured after the change: a sub-agent's search served in 0.6 s during a 17.7 s model call. What remains is Claude Code's own: it sends the MCP calls of one assistant turn one after the other.
- **Where**: `runStdioProxyWith`, `bridgeParallel`, `requestID`, `rpcErrorLine` in `cmd/mesh7/proxy_stdio.go`; tests in `cmd/mesh7/proxy_stdio_test.go` (run with `-race`). Docs: `flux7-docs/docs/mesh7/deployment-modes.md`.
